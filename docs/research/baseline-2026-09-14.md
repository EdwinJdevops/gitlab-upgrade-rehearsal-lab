# Baseline: official GitLab upgrade machinery on 2026-09-14

Status: frozen research baseline for M0

This document records the vendor capabilities that every experiment must beat. A historical failure does not count as project value if current GitLab already catches it.

## Authoritative upgrade path

GitLab's `config/upgrade_path.yml` is the single source of truth for required stops. The GitHub mirror revision observed for that file on 2026-09-14 was `769726ce26ccfb52fb9c8b2a3adf34bbeadb29f9` (mirror commit dated 2026-03-30). The current schedule includes predictable stops at 18.2, 18.5, 18.8, 18.11, 19.2, 19.5, 19.8 and 19.11, with older and conditional stops retained as historical data.

Source:
- https://gitlab.com/gitlab-org/gitlab/-/blob/master/config/upgrade_path.yml
- mirror: https://github.com/gitlabhq/gitlabhq/blob/master/config/upgrade_path.yml

## Support Upgrade Path and alerts

GitLab Support's Upgrade Path project consumes `upgrade_path.yml`, publishes a machine-readable `path.json`, and maintains `alerts.yml` with applicability range, severity, required version, timing (`preupgrade`, `upgrade`, `postupgrade`) and remediation guidance.

Source:
- https://gitlab.com/gitlab-com/support/toolbox/upgrade-path
- https://gitlab-com.gitlab.io/support/toolbox/upgrade-path/path.json
- https://gitlab.com/gitlab-com/support/toolbox/upgrade-path/-/raw/main/alerts.yml

Design consequence: this repository must consume official data. It must not maintain a competing upgrade-rule database.

## GitLab Detective

GitLab Detective is a GitLab Support diagnostic tool for Self-Managed installations. GitLab documents it as read-only and intended to detect known misconfigurations, deprecated/removed settings, and known issues before upgrades. The support article was updated 2026-04-07. The public project remained active in September 2026. An upgrade-alerts mode was still under active design in MR !244 and consumed Support Upgrade Path alerts.

Sources:
- https://support.gitlab.com/hc/en-us/articles/20778829788572-Use-GitLab-Detective-as-a-part-of-preparing-to-upgrade-GitLab
- https://gitlab.com/gitlab-com/support/toolbox/gitlab-detective
- https://gitlab.com/gitlab-com/support/toolbox/gitlab-detective/-/merge_requests/244

Design consequence: a thin preflight wrapper around known diagnostics has no defensible value.

## Multi-version database migration testing

GitLab's `db:migrate:multi-version-upgrade` CI job validates migrations from the latest required stop to the working branch using a PostgreSQL dump populated with test data. The dump is generated by `pg-dump-generator` using Data Seeder and `db:seed_fu` fixtures and is refreshed in scheduled pipelines.

The GitHub mirror revision observed for the current documentation was `73cca2f2b023cb87a90f55610c8e4e812f42aa75` (2026-08-26).

Sources:
- https://docs.gitlab.com/development/database/dbmigrate_multi_version_upgrade_job/
- https://gitlab.com/gitlab-org/quality/pg-dump-generator

Design consequence: data-dependent migration fixtures must demonstrate signal beyond GitLab's seeded migration test, not merely reproduce an old migration bug.

## GitLab QA upgrade scenarios

GitLab QA currently documents `Test::Omnibus::UpdateFromPrevious` and `Test::Omnibus::UpdateToNext`.

`UpdateFromPrevious` deploys an earlier version, runs health/smoke tests to populate state, resolves the official upgrade path, upgrades gradually, and executes tests. `UpdateToNext` covers development-to-next-stable upgrade transitions.

Source:
- https://gitlab.com/gitlab-org/gitlab-qa/-/blob/master/docs/what_tests_can_be_run.md

Design consequence: generic 'rehearse an upgrade' is already vendor territory. Our experiment must be specifically about customer/historical state that representative QA-generated state does not model.

## GitLab operator guidance

GitLab's current upgrade plan explicitly tells Self-Managed administrators to:

- resolve the supported upgrade path;
- run upgrade health checks;
- create and test rollback plans;
- test the upgrade plan in a clone of production;
- ensure background migrations complete before each upgrade;
- verify configuration, encrypted data, sign-in, repositories, Git operations, runners, registry and optional systems such as Geo or Elasticsearch.

Source:
- https://docs.gitlab.com/update/plan_your_upgrade/

Design consequence: the experiment is validating whether this recommended production-clone rehearsal can be made reusable and evidence-producing, not inventing the practice.

## Restore constraints

GitLab restore documentation requires a working destination at the exact same GitLab version and CE/EE type as the backup. GitLab secrets must be restored for encrypted database values and authentication-dependent behavior. Some storage/configuration relationships must also match the original environment, while object-storage state is not implicitly reconstructed by a normal restore.

Source:
- https://docs.gitlab.com/administration/backup_restore/restore_gitlab/

Design consequence: v0 uses synthetic/sanitized fixtures. Real customer-state ingestion is explicitly deferred.

## Customer upgrade working-group signal

A 2026 GitLab Customer Upgrade working-group issue states goals around reducing upgrade-related emergency support cases, improving database health/pre-upgrade diagnostics, and expanding multi-version upgrade testing. Some observations in that issue predate later seeded migration-test improvements, so they are treated as historical direction rather than a complete description of today's test coverage.

Source:
- https://gitlab.com/gitlab-org/gitlab/-/issues/591711

## Baseline verdict

The current vendor baseline already covers:

1. authoritative path planning;
2. version-scoped upgrade alerts;
3. read-only diagnostics for known upgrade hazards;
4. current-state health and configuration checks;
5. seeded multi-version database migration testing;
6. controlled GitLab QA upgrade scenarios;
7. documented clone-of-production and rollback rehearsal guidance.

Therefore an M0 fixture counts as a meaningful replay win only if it demonstrates a materially important state-dependent failure that:

- current baseline mechanisms do not detect before transition execution;
- isolated replay does detect;
- cannot reasonably be reduced to a cheap deterministic upstream check; and
- is reproducible through the same reusable harness as at least one materially different failure class.

Anything weaker is `absorbed_upstream`, `baseline_detected`, or `not_differentiated` and does not justify productization.
